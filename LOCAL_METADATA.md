# Local metadata safety

Frameline stores its own metadata in Electron's user data directory. It does not edit the selected FCPXML export or a Resolve project when recording an observation. Version 5 maps SHA-256 fingerprints of absolute export paths or opaque Resolve API project IDs to separate randomly generated local project IDs, revision summaries, branch heads, a selected branch, legacy nullable sync bases, and service-scoped shared-base receipts. Version 1 project IDs and version 2 revision history migrate without change; existing history becomes `main`. The path-free Resolve project display name is retained locally for offline history browsing. No project paths or media paths are stored in this file or sent to the renderer.

`metadata.json` is written through a temporary file and rename. `metadata.json.bak` holds the prior valid state, or the first state after initial creation. If the primary file is damaged, Frameline preserves it as `metadata.json.corrupt-<id>`, restores the backup, and reports recovery. If neither copy is valid, it stops metadata writes and shows an error. A file with a newer schema version is never rewritten by an older app.

Publication flushes the temporary metadata file, backup bytes, and containing directory around replacements before acknowledgment. A failure after primary replacement is attempted returns `metadata-storage-uncertain` and latches that store instance until reopening; the caller cannot assume the previous state remains on disk. Prepublication failures do not acknowledge a new base. A fresh store validates saved primary/backup state through the ordinary recovery rules.

Each saved revision has its own immutable JSON file under `revisions/<project ID>/`. It contains a validated scan manifest, source content hash, parent revision ID, author label, timestamp, message, and manifest version. An FCPXML revision records an unknown editor version; a verified Resolve API observation records its exact observed version and the source-bound schema-3 snapshot. The metadata index is updated only after the revision file is written and synced. A crash between those steps can leave an unindexed file, which is kept for future recovery. The app checks the source FCPXML hash again before saving and refuses a stale scan. A Resolve observation revision preserves what the verified capture reported; it does not prove the project is still unchanged or authorize apply. Index validation rejects duplicate project or revision IDs, broken parent links, and revision cycles before history is used.

New revision summaries also store a SHA-256 hash of the record file. Opening a revision verifies that hash, checks the manifest schema, and confirms its metadata matches the index. Records saved before this hash was added are still readable through the schema and index checks. A missing or changed record is reported without exposing its local path.

Resolve observation manifest versions are separate from the metadata index version. Manifest schema 1 hashes its snapshot. Schema 2 preserves that snapshot hash and separately hashes a portable transaction audit. New normal richer captures use manifest schema 3: `sourceHash` and the revision's `contentHash` cover the complete serialized property/track/effect observation, while `snapshotHash` binds the duplicate schema-3 snapshot component used by snapshot-only preview and optional FCPXML matching. Validation checks both hashes and exact agreement of the two snapshot copies. Property-only edits can therefore create distinct immutable revisions without inventing snapshot changes. Existing records are not rewritten. Readers that do not recognize manifest schema 3 reject those records.

History compares richer observations, including validated supplements in older trial audits, only where coverage exists on both sides. Missing coverage is reported explicitly. Returned properties, effect slots and track indexes do not establish complete native semantics or persistent track/effect identity. New coverage may be saved even when snapshot fields match; an equivalent observed state does not create a duplicate through the capture save flow. The reviewed revision-backup format preserves schema-3 manifests and their complete observations. Save capture JSON exports the complete verified observation; Save snapshot JSON exports only its snapshot component. Both publish validated bytes privately to a new filename without replacing an existing file or link. History preview includes richer observations by default, including validated result supplements from older trial audits. Clearing its checkbox deliberately selects snapshot-only compatibility. Rich live previews bind the complete current observation hash, so a property-only recapture invalidates a stale source reference. Full-source preview plans use schema 2; snapshot-only plans keep schema 1 and their existing immutable artifact meanings. Three-way property/effect-slot/track-state values require comparable reads on all three sides; missing reads remain coverage gaps. See `phase-0/THREE_WAY_PREVIEW.md`.

Branch names use 1–40 lowercase letters, numbers, dots, underscores, or hyphens and start with a letter or number. Creating a branch copies the selected branch's head and switches to it. Saving a revision compares the expected branch head before writing, then advances only that branch. History follows the selected branch's parent chain. The selected branch persists across app restarts.

Every metadata read and write takes an exclusive `metadata.lock` in the user data directory. This serializes separate app processes and store instances, so each revision save checks its expected branch head against the latest metadata. An active lock that lasts more than five seconds produces a retryable error without changing metadata. A lock left by a process that has exited is reclaimed; an incomplete lock file is reclaimed after five seconds. The lock is removed when the transaction finishes. If a lock remains because its process ID was reused, close the other instance or remove `metadata.lock` only after confirming that no Frameline process is using that directory.

History can be exported as a versioned `.json` backup containing all local branches and their verified revision records. Version 1 contains FCPXML scan revisions; version 2 also permits Resolve API observation revisions. Import checks the package format, each record hash and manifest, all parent links, branch heads, and project source kind before writing. Resolve observations may only enter history for the same Resolve API project ID. Imported records receive new local IDs and appear on `import-<branch>` branches; existing history and the selected branch stay in place. The package contains read-only observations, not the FCPXML source or media files. Import is limited to 50 MB. If a write fails after record files are created but before the index is updated, those files remain unindexed for recovery.

Future metadata changes must increment `schemaVersion` and migrate a validated copy before replacing the primary file. Tests must cover upgrade, interrupted write, backup restore, and refusal to downgrade. A moved export initially receives a new local ID. An explicit relink can move a verified old project's history to that path only when the selected export's hash equals the old project's current-branch head and the new ID has no revisions or branches. The old path mapping is removed, so reopening it creates a fresh ID. No path is stored in the metadata index or sent to the renderer. Identical copies of a file can both be candidates; the user must choose the intended history.

The legacy schema-v4 `syncBases` field stores a nullable revision ID per branch. A new branch inherits that legacy value, and imported branches begin with an unknown value. Schema 5 preserves these values while adding an empty `serviceSyncBases` list on migration; no legacy value becomes evidence of service synchronization. Transfer bundles omit both local base stores.

Current Check/Push/Fetch operations can record a [service-scoped shared base](SERVICE_SHARED_BASES.md), bound to origin hash, account, local project/branch, and remote project/branch. The private receipt references exact local bytes and an immutable, independently readable remote proof snapshot. Expected head/base-version checks, full ancestry verification, and historical remote-prefix continuity protect updates; restart revalidates the witness/local bytes. In-session display can reuse a verified historical observation until its scope/generation/receipt changes. Check/Push proof snapshots do not advance the explicit Fetch display index. These receipts establish saved metadata correspondence, not current source/editor/media state or apply readiness.

Media audit jobs use a separate `media-audits/media-jobs.json` journal in the user data directory. Its records contain local project and job IDs, the selected export's hash, source/copy role, a sanitized export display label, attempt and progress data, timestamps, coded failures and a completed-report reference. The selected export and media locations are not persisted in the journal. Job writes use a private temporary file, sync and atomic replacement. The queue is single-process; it does not provide distributed worker leases.

Completed path-free reports are stored under `media-audits/reports/<content hash>.json` with private permissions and nonreplacing publication. Their contents include dependency display names, availability, sizes and media fingerprints. Reading a report checks its content hash, schema, counts and export binding. Report files are retained independently of the mutable job record; this is not an immutable audit-attempt history, and report garbage collection is not implemented. The renderer receives source fingerprints and report summaries, but not media paths or media fingerprint hashes.

On startup, running jobs return to the queue and wait for explicit restart. Their source must be rebound to the same selected local project ID and export hash. Copy checks also require a freshly verified review copy. Restarting reads the files again from the beginning; a persisted percentage does not represent resumable hash bytes. A completed report can be shown after the matching export is selected, but remains a record of its last check rather than evidence that the files are still unchanged.

Native verification recovered a completed media report after another app restart and matching-source selection without rehashing. The job retained its run ID and completion timestamp, and the stored report hash verified against the same dependency counts. See `phase-0/media-audit-jobs-live-observation.json` for the disposable-fixture evidence.

The shared-base milestone passed all 717 tests and 273 security tests. Its native migration preserved the complete legacy project rows for 10 existing projects and 20 revisions; a disposable shared-base receipt recovered with identical IDs/time after a full app restart. See `SERVICE_SHARED_BASES.md` for process, browser, storage-failure, and compatibility limits.
