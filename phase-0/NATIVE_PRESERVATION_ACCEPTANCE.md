# Native preservation acceptance

The personal target is the installed Resolve Free21.1.2/build21.1.20010 on macOS. The preservation gate concerns fields required for a lossless edit and editor round trip, including native values the API cannot expose. Rich-state or seven-family equality is insufficient. Ordinary Apply remains disabled.

Four distinct proofs are required:

1. **Identity and source binding.** The original archive hash, project/timeline/item UUID parentage and unique direct `Name` text span must agree. A declared offset or UUID in a report is not identity proof. Wrong, ambiguous, stale and unsupported sources refuse.
2. **Writer byte preservation.** For the accepted archive envelope, every decompressed native member name, order and byte is retained except the exact declared name span. Unknown opaque payloads, XML syntax, attributes, unrecognized values and unrelated binary members are not decoded and rewritten. The ZIP writer independently retains physical metadata and untouched compressed records, accounting only for required CRC, size and offset updates. Unsupported envelopes refuse rather than discard unknown data.
3. **Actual editor execution.** A separate source-bound disposable import/open/reopen/export program must verify its exact prepared input and execution chain, retain failures and backups, and observe the intended edit on the correct object. Importing a copy to establish a new baseline is not evidence that import itself is lossless. Freshly observed IDs must not be presented as source-ID continuity.
4. **Editor round-trip preservation.** Compare the written native members with the actual re-exported members, including every unknown value. Unexplained changes, additions, removals or substitutions fail. No-op controls help locate changes caused by reading, saving, reopening or exporting; they do not establish that a changed opaque field is harmless. No native field is excluded merely because it changes in a control.

Exact re-exported member equality is a sufficient criterion, not the only possible proof. A complete comparison of authoritative persisted native state could instead establish value preservation despite different export serialization. The [separate read-only SQLite experiment](NATIVE_SQLITE_PRESERVATION.md) therefore checks the entire closed project directory and every schema object, table, row and typed cell, including all unknown BLOB/TEXT values. It has no column exemptions. This alternative requires actual closed/checkpoint chronology and complete storage coverage; a subset of known tables or API-visible values would not suffice. DRP differences remain reported, not labelled harmless by assumption.

The [raw-byte checker](native-preservation-acceptance.js) accepts member records `{nameBytes: Buffer, bytes: Buffer}` in archive order. `compareExactNativeMembers(before, after, edits)` reconstructs one authorized `Name` span exactly and accounts for all other supplied bytes. With no edit, it requires exact member equality. Difference records retain hashes, byte lengths and bounded differing ranges without exposing values or member names.

`assessNativePreservationRoundTrip` recomputes source-to-written and written-to-re-exported comparisons. `requireNativePreservationRoundTripBytes` rejects either unexplained-difference verdict. Even a successful supplied-byte comparison deliberately leaves `losslessValidated`, `editorRoundTripPreservationProven` and `gateEvidenceComplete` false: this primitive does not independently establish UUID-to-span binding, ZIP envelope preservation or actual editor execution. A later source-bound evidence auditor must establish those separate facts before promoting the gate.

Nine adversarial tests cover unknown XML syntax and binary bytes, non-UTF8 member names, stale spans, duplicate/missing/added/substituted members, physical order, opaque same-length changes, malformed/accessor input and bounded diagnostics. They also assert that a successful byte comparison alone cannot authorize editing or a preservation claim.

The first independent native writer check preserves all five actual member payloads outside the declared span, with four members exactly unchanged. This establishes a writer boundary result only. The existing read-only native export control already contains opaque changes; none is normalized away. The editor round-trip verdict remains pending actual complete-byte comparison.
