# Durable local collaboration service

`createDurableCollaborationService` in `src/durable-collaboration-service.js` combines identity, access control, immutable revision history, project activity, revision comments, branch approvals, read-only sharing, and notification preferences/outbox, and team project templates in one encrypted, versioned local state. Disposable process-restart and injected-failure checks passed. The runtime backs the optional self-hosted HTTPS service and desktop connection; it does not configure public deployment or provide a production database.

## State and trust boundary

The combined schema-7 state contains a generation, a private random pagination-signing secret, identity and access snapshots, schema-3 immutable history, version-1 project activity with recipient read receipts, version-1 immutable-revision comments with hashed creation receipts, version-1 branch policies/approval requests with scoped receipts, version-1 share links with capability hashes and creation receipts, version-1 notification preferences, consent epochs, jobs, and mutation receipts, and version-1 team templates with saved-version and project-creation receipts. Its private records include salted password hashes, hashed session/recovery credentials, team and project memberships, invitation digests, project tombstones, revisions/manifests, branch heads, exact-request idempotency records, private event recipients, and comment bodies/anchors/resolution records. Bearer tokens are returned when issued and are represented by digests in saved state. Private snapshots contain emails and credential hashes; they are trusted service inputs, not public response objects or renderer data. The outer encrypted file format remains version 1.

The host supplies an encryption keyring, and the runtime writes AES-256-GCM envelopes with a key ID to `collaboration.enc.json`. It does not create a key file. Keys must be kept outside that file and supplied again when opening it. The private directory requires mode `0700`, and state files use `0600`; symlink state files are refused. The decrypted state is bounded to 64 MiB and the encrypted file to 96 MiB. Missing keys, tampering, unsupported schemas, or invalid cross-state references fail closed. Encryption does not replace host security or per-request authorization.

Opening defaults to `initialize: false` and refuses a missing directory or state file. Trusted first-time provisioning must explicitly pass `initialize: true` to create a blank store; it creates no accounts. Once a runtime has opened successfully, losing its state file fails closed even if it was originally initialized with that flag. Reopening does not silently recreate lost state or fall back to a backup. A trusted caller can deliberately initialize an empty directory as a separate provisioning action.

Recovery validates identity/access/history/activity/comments/branch protection/share links/notifications/project templates together. Access registrations must match history projects, membership and revision authors must reference known users, and active project roles and team owners require active accounts. Historical authors and permitted tombstone references can remain after account deletion. Manifest hashes, revision parent/project bindings, cycle checks, saved idempotency results, the activity hash chain, and event/recipient/subject references are revalidated. Comment authors and resolvers must reference known users; each anchor must resolve within the exact project/revision's validated Resolve manifest. Restoring the snapshots does not replay membership events or create historical comments.

History schema 3 stores manifests by a project-scoped key while preserving their public canonical `sha256:` IDs. Identical manifest bytes can therefore belong independently to two projects without a collision or cross-project lookup. Opening valid history schema 1 or 2 validates its original scope, migrates it, and atomically publishes the upgraded encrypted state. Existing revision IDs, branch heads, and available idempotency records are preserved. Encrypted-upgrade and same-content/two-project regression checks passed in the later 539-test desktop-integration suite, which had no failures or skips and passed packaging validation.

Opening valid combined schemas 1 through 6 atomically publishes schema 7 with empty project-template and creation-receipt state. Schemas 1 through 5 also receive empty notification state. Schemas 1 through 4 also receive empty share-link state. Schemas 1 through 3 also receive empty branch protection; schema 4 preserves its policy and approval history. Schemas 1 and 2 receive empty comments and creation receipts; schema 1 also receives empty activity and read receipts. Existing activity and schema-3 comments are preserved. Identity, access, history, and IDs are preserved without event or comment backfill. Future schemas and downgraded records carrying newer fields are refused. New domain events and recipient-owned read receipts share the runtime transaction; no-op and idempotent mutation retries do not duplicate events. Activity is bounded to 16 MiB, 20,000 events, 100,000 recipient references, and 100,000 receipts. See [project activity](PROJECT_ACTIVITY.md) for authenticated cursor pages, privacy, and validation status.

Comment creation and one-way resolution share the same transaction and acknowledgment boundary. Comment state is bounded to 16 MiB and 20,000 comments with one hashed idempotency receipt per comment. Creation keys are scoped to authenticated actor/project/revision, and anchor cross-validation keeps service project IDs separate from Resolve API UUIDs. All current roles can read; owner/editor posting and author/current-owner resolution are checked on every request. See [revision comments](REVIEW_COMMENTS.md) and the [live observation](phase-0/revision-comments-live-observation.json) for the desktop/HTTPS workflow and its immutable-observation boundary.

Branch policy changes, approval requests, independent approvals, branch updates, applied receipts, and their activity share the same encrypted transaction. Recovery verifies policy history, exact revision parents, approval identities and timestamps, applied branch ancestry, and matching audit events. See [branch approvals](COLLABORATION_FOUNDATIONS.md#branch-approvals-on-a-self-hosted-service) for the desktop workflow, limits, and retry semantics.

Share-link creation and revocation commit their scoped receipts, capability hashes, immutable revision/manifest bindings, and matching activity in the same encrypted transaction. Links never persist a plaintext token. A private domain-separated HMAC supports exact lost-acknowledgment creation retry without issuing a duplicate link. Recovery verifies token derivation, issuer/revoker identities, revision scope, receipts, and matching activity. Anonymous reads recheck expiry, revocation, issuer ownership and active account, and project deletion. See [read-only sharing](COLLABORATION_FOUNDATIONS.md#read-only-sharing).

Notification preferences and exact-request receipts commit with consent changes and cancellation of pending jobs. First enablement captures the activity append position, preventing historical email backfill. A mode/hour change creates a new consent epoch; old unsubscribe tokens cannot disable new consent. Only capability hashes are stored. Account-wide inbox reads reuse the activity recipients and read receipts; access loss hides inaccessible details while preserving generic notices addressed to the removed account. See [account updates and email preferences](PROJECT_ACTIVITY.md#account-updates-and-email-preferences).

The private notification snapshot is bounded to 16 MiB, 10,000 preferences, 10,000 consent epochs, 10,000 jobs, and 20,000 idempotency receipts. A job contains at most 100 event references. Normal mutations reserve 1 MiB of that budget for terminal delivery/opt-out updates. Capacity failures refuse new work; no automatic pruning is implemented. Combined-state limits still apply.

Scheduling, lease claims, preparation, delivery acknowledgment, and retry/failure transitions use the same durable transaction boundary. SMTP waits outside the runtime lock. Preparation rechecks the active account, current consent, unread events, and project access; a second preparation before SMTP DATA can cancel or redact stale work. A final accepted message can still race a subsequent access or consent change and cannot be recalled. Jobs recover expired leases after reopening and retain stable Message-IDs across at most five attempts. Lost SMTP acknowledgments may duplicate mail; these receipts do not establish exactly-once external delivery. The [host guide](SERVICE_HOST.md#optional-notification-email) describes configuration, retry timing, and operator responsibilities.

Team templates are team-scoped. Current members can list them; only a current team owner can save, preview, or create projects. A preview binds actor, team, template/version, name, branches, and media classes. Creation saves the history project, owner registration, empty `main` plus template branches, immutable initial class policy, and intent receipt in one collaboration transaction. No second asset-store write or filesystem media operation is required for that commit. Creation grants only its owner's project access, without copying team members into project roles.

A template-created project's initial policy is a read-only version-1 baseline. The asset store consults that baseline and persists later owner overrides at version 2 or above. Ordinary projects retain the default empty version-0 policy. Changing a template never resets an existing project's policy. Without a configured asset service, previews disclose availability and creation refuses nonempty media classes; metadata-only templates still work.

The template snapshot is bounded to 16 MiB, 1,000 templates, 10,000 save receipts, and 10,000 creation receipts. Each template permits 20 additional branches and the five known media classes. Hydration verifies complete saved version transitions, historical templates in creation receipts, actor/team references, project ownership/history bindings, and initial policy provenance. Exact save/create replay authenticates the current owner before returning its historical committed receipt; it does not recreate a deleted project, advance a template version, or reset an override. Capacity failures refuse new work; pruning and deletion workflows remain separate.

The desktop's separate `project-preset-intents.js` journal stores one pending save/create per origin/account binding, bounded to 100 bindings and 2 MiB. It is private local JSON rather than a service backup: mode `0700` directory, `0600` regular files, bounded nofollow/nonblocking reads, serialized/cooperatively locked updates, and file/rename/directory flush before acknowledgment. A failure after rename is attempted latches uncertainty until a fresh factory validates disk. A used journal that disappears fails closed. The record contains template/project intent and its original creation plan, UUID retry identity, and timestamp; passwords, session tokens, and raw origins are absent. Renderer state omits the retry key. Startup reads the journal without replaying a network request; sign-out preserves isolated account records.

An explicit retry recovers an ambiguous service commit. Explicit dismissal after checking the service removes only the local intent; it cannot undo the service operation and loses the identity needed to prevent a duplicate new request. Service state and this journal have separate acknowledgment boundaries, so a verified service result can coexist with a pending local cleanup retry.

The combined state does not persist separate audit trails or rate-limit buckets. Those foundations still need durable integration.

## Transaction behavior

The asynchronous factory returns identity, team, project, membership, and authorized history facades, plus status, encryption rotation, and close operations. It exposes no mutable domain-store handles. Every operation joins the runtime's serialized queue, obtains a cooperative local metadata lock, rereads current disk state, and hydrates fresh stores. A mutation validates the combined result and canonical encrypted envelope, then decrypts that envelope to verify an exact validated-state round trip before replacement. An invalid or mismatched keyring cannot replace the old file. The runtime writes a private temporary file, flushes it, renames it over the state file, and flushes the directory before returning success. This also lets cooperating local runtime instances merge against the latest committed state.

An operation or persistence failure before a rename is attempted returns no committed acknowledgment, leaves the previous file intact, and discards that operation's hydrated stores. Any failure after a rename attempt, including a rename that took effect before reporting an error, leaves durability uncertain. Directory-flush and lock-release failures are also treated as uncertain. That runtime then refuses further operations until it is reopened; the caller must not assume the mutation failed to reach disk. A reopened runtime validates the current file and does not automatically restore an older backup.

The HTTP handler receives the authorized `service` facade. Authentication and authorization run for every project request, including after reopening. Persisted idempotency and compare-and-swap records let retry recover a committed result; the disposable restart proof verified revision reuse without duplicates after reopening the encrypted store.

Recovery delivery is optional and host supplied. Beginning recovery without a configured callback is refused. When configured, the callback is scheduled after the recovery-token digest is committed; delivery is detached so a pending provider cannot stall later transactions or close. Callback failure remains generic and does not roll back committed state. Account-recovery delivery has no durable outbox or delivery guarantee. The notification outbox is separate and does not deliver recovery links.

`rotateEncryption` writes the combined state with the supplied next keyring before switching this runtime to it. Ordinary mutations cannot change the saved key ID and return `collaboration-key-rotation-required` if their keyring would do so. This prevents an older instance that can decrypt both keys from silently reverting the active key policy. Other instances must hold a keyring that can decrypt the new key ID and encrypt ordinary writes with it. `close` rejects new operations and waits for already-queued transactions, without awaiting detached delivery callbacks. The host owns the listening server, TLS, timeouts, key custody, and service shutdown, and must stop/drain its notification worker before closing the runtime.

The local lock is not a distributed lease, and the file protocol is not a production database transaction system. Filesystem- and hardware-specific power-loss guarantees require separate validation. Generation matching detects inconsistent envelopes but provides no anti-replay guarantee: restoring an older valid encrypted file can restore older session, permission, consent, or pending-delivery state. Trusted restore policy and external rollback protection remain open.

## Validation

The [disposable process/network observation](phase-0/durable-collaboration-live-observation.json), reproduced with `node scripts/durable-network-sync-proof.js`, recorded 38 actual HTTP requests across three owned server processes on fresh loopback ports. Two authorized accounts used the same encrypted local store and externally supplied key. The proof verified:

- An acknowledged branch update survived `SIGKILL`; sessions, owner/editor roles, and two immutable revisions recovered in a fresh process.
- Retrying recovered history created no duplicate revisions, and new revision authors remained bound to the authenticated session.
- Forged authentication was denied, and member removal, refresh rotation, sign-out, and refresh-token revocation remained effective after later process restarts.
- The state file had mode `0600`, credentials were absent from plaintext storage, and all owned child processes were verified terminal before replacement and final cleanup. The saved observation contains no credentials or local paths.

Separate runtime checks passed for cooperating concurrent writers, domain-failure rollback, recovery state and detached delivery, temporary-file flush failure before publication, and uncertain rename/directory-flush failures followed by validated reopen. They also cover invalid or mutating keyring output, refusal of stale-key downgrades, dangling references, history cycles, future schemas, tampering, file permissions, symlinks, missing-state refusal, and account deletion with historical references and email-reuse isolation. Strict identity and access snapshot tests passed as part of the same full suite.

The original runtime milestone passed all 495 tests without failures or skips and passed packaging validation. The later revision-comment integration passed all 872 full-suite and 485 security tests without skips, including schema-1/2-to-3 preservation, comment cross-reference corruption, concurrent appends, pre-publication failure rollback, and uncertain-write reopen with exact retry. Its browser/native HTTPS evidence is linked above. The process kill followed an acknowledged update. These results do not claim a crash during a write, a machine power-loss test, production key custody, or deployed cross-device operation. Project tombstone/account-removal recovery was covered by local runtime tests rather than the HTTP process fixture.

The later branch-protection milestone passed all 963 full-suite and 576 security tests with no skips, plus package validation. Its actual HTTPS proof issued 58 requests across three hosts and three clients, covering blocked publication, independent review, lost acknowledgment recovery after a policy change and reviewer removal, and current-publisher denial after revocation. Native/browser checks verified the real queued push → review → approval → explicit Retry flow. See [live evidence](phase-0/branch-approvals-live-observation.json).

The later share-link milestone passed the 1,057-test full suite and 670 security tests without skips, plus package validation. Thirteen core/runtime tests cover capability hash/receipt/audit corruption, schema-1–4 preservation including nonempty comments and applied approvals, concurrent creation/revocation, pre-publication rollback, and uncertain-create reopening with exact capability recovery. Its 62-request HTTPS proof uses three actual launcher processes and three clients. Native and recipient browser checks are recorded in [sharing evidence](phase-0/share-links-live-observation.json); 75 focused viewer/controller/renderer checks passed after the final count-label correction.

The notification integration's `tests/self-hosted-notifications-proof.test.js` passed 44 actual HTTPS requests across three host and three client processes with the same encrypted store. It verified a background message accepted by an owned loopback TLS fake MTA, preference retry after a deliberately lost acknowledgment, persisted read receipts, consent-epoch opt-out, and generic notices after member removal/project deletion. Global opt-out remained available after project access ended. No external email, production mail provider, mid-write crash, or power-loss guarantee was tested.

The template test `tests/project-presets-https.test.js` passed 69 HTTPS requests across three real launcher and three client processes. Exact save/create retries survived deliberately discarded successful acknowledgments, template changes, and restart. Team-role boundaries, preview actor/name binding, empty branch creation, initial-media-policy provenance and later override independence, missing asset-service gates, and deleted-member/revoked-session denial passed. This is disposable loopback process evidence, separate from native desktop validation and production deployment.

This runtime remains a local service foundation.
