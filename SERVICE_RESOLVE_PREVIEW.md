# Resolve service history preview

The Resolve preview can now use a verified service history as its incoming side. It combines an exact service-scoped shared base, an explicitly fetched Resolve revision, and either a saved local Resolve branch head or a recently accepted Console capture. The existing observed-field classifier and conflict review remain read-only. This connects service metadata to API-ID-based Resolve review without importing revisions or enabling editor writes.

## Workflow

Sign in through History's service account controls. In Resolve preview, select a saved Resolve project and local branch. **Resolve service history** has its own branch mapping, push queue, fetched cache, and shared-base scope; it does not borrow the selected FCPXML/media mapping. Link an accessible service project/branch, use **Push observations** where authorized, and explicitly **Fetch history** to capture incoming metadata. Viewers can fetch and preview but cannot push.

Choose **Saved branch head** or **Latest verified capture**, then **Preview service history**. Saved-head mode reads the immutable selected branch record and works without a new Console capture. Capture mode requires an accepted complete observation from the matching API project, with a valid request receipt no more than five minutes old. A new capture or a changed selection requires rebuilding the preview.

The preview uses the existing field list, base/local/incoming values, warnings, and conflict choices. Its provenance disclosure shows the source mode, revision IDs, source hashes, fetch time, and capture acceptance time where applicable. Conflict choices record review intent. They do not authorize a rename drill, save a resulting revision, or apply anything to Resolve.

## History and source verification

The service client transfers validated Resolve observation manifests, including manifest-v3 complete property/effect/track observations. A property-only edit can change the complete source hash while the embedded snapshot hash remains unchanged. Sources preserve the complete observation where present; older snapshot-only observations retain explicit missing-coverage gaps.

The main process reconstructs the [scoped shared-base proof](SERVICE_SHARED_BASES.md) from immutable local records and the saved witness. It validates the explicitly fetched incoming graph and exact historical remote prefix through that base. All roles must be Resolve observations of the same API project and compatible exact Resolve version. A remote revision's source ID, project name, or similar clip names cannot substitute for this ancestry and manifest verification. Different API project IDs fail closed; identity across copied/imported collaborator projects is not established.

`createServiceResolveComparison()` takes the same exact six history/source inputs as the service comparison binder, plus a separate local verification receipt. Saved-head receipts are exactly `{mode: 'saved-head'}`. Accepted-capture receipts contain exactly `{mode: 'verified-capture', generation, requestId, requestSha256, acceptedAt}`. Generation must be positive, request IDs use the actual 32-hex-character Console protocol, request hashes are SHA-256, and acceptance must be neither future-dated nor more than 300,000 ms old.

The private result retains the scope, receipt and immutable ancestry bindings, exact role source strings, recomputed Resolve plan, and content ID. The renderer receives an explicit summary and the existing review display, without credential material, private proof hashes, or local paths. Reopening or refreshing a service-derived review privately rebuilds its source binding; changed generation, observation bytes, scope, base, or incoming evidence cannot reuse an earlier binding.

Preview and source revalidation make no network request and write no revision, branch, base, source, or cache. Newer remote work requires another explicit Fetch. Preview state stays in memory and is not automatically restored after app restart. Cached history and shared-base evidence can recover independently. Scope/account changes, source replacement, expiration, or incompatible history invalidate service-derived review. The wrapper's private source getter is not a preload API.

## Scope and limits

The plan classifies only represented, comparable observations. Returned properties, effect catalogue/slot observations, and indexed track state do not establish complete editor semantics or persistent effect/track identity. Missing reads remain gaps. The three role sources are bounded to 20 MiB each and the plan to 31 MiB, in addition to history/cache limits.

An accepted Console receipt establishes which copied observation this app accepted and when. It does not authenticate the editor, prove the project has remained unchanged since capture, or establish a live cross-device branch. No editor mutation, revision import, media transfer, or `pull.completed` event follows from previewing. The ordinary apply path remains disabled, and existing experimental rename/recovery restrictions remain separate.

## Validation

The [recorded network observation](phase-0/service-resolve-preview-network-observation.json) passed 55 actual HTTPS requests across two host processes and two fresh client/controller workers. `node scripts/service-resolve-preview-proof.js` reproduces the exercise; its dedicated test also passed. Two real CLI-provisioned publisher/viewer accounts shared a manifest-v3 common root. Private disposable local histories were seeded with the same immutable root; the publisher added a property-only Pan observation through the actual authorized service.

Saved-head preview reported incoming-only Pan. A synthetic accepted-capture receipt bound a different Pan value and an independent Tilt edit, yielding a property conflict plus local-only change. Exact role sources reproduced and verified the mature Resolve plan. Completing that service-derived conflict review still refused the rename drill's verified-review getter. Scope/base/incoming substitution, changed capture generation, changed observation bytes, expired receipts, and future timestamps were refused. A fresh worker recovered cached history and base without restoring a preview. The viewer could not push, selection changes retired old bindings, and no pull-completion event was emitted.

Request counters and private-file hashes verified that Preview and its source recheck made no network dispatch or file mutation. Private local/cache files used mode `0600`; all owned processes terminated before replacement and cleanup. The observations came from checked-in disposable complete-capture fixtures, and their request receipts were synthetic protocol fixtures. This proves service/provenance control flow, not live editor authenticity. The CA was trusted only inside isolated numeric-loopback workers.

All 771 full-suite tests, 329 security tests, and packaging validation passed with no test skips. Two regressions verify that in-flight private reads cannot expose or resurrect retired previews; in-memory negative controls reproduced both prior failures. The [desktop observation](phase-0/service-resolve-preview-desktop-observation.json) records two browser rounds at 1440, 768, and 390 px with no horizontal overflow; button heights were 38, 38, and 44 px. The browser fixture used the actual request/response parser around synthetic Console output containing 53 items and 443 returned property values. Saved-head mode showed incoming Pan 13.25; an accepted fixture capture showed Pan 26.5 conflict and independent local Tilt 5. Keep local completed the review audit, unchanged revalidation retained that choice, and preparing an identical new capture cleared old choices before rebuilding one unresolved conflict.

A viewer signed in independently, linked its own scope, and required its own explicit Fetch before previewing; the owner's base/cache were not borrowed. Saved-head Pan preview was available, Push remained disabled, and sign-out hid service provenance.

Native Electron used actual IPC and OS-backed sign-in, then the product's reviewed backup import to create one disposable root on `import-main` with remapped local revision IDs. That branch linked to `native-resolve/main` and pushed its root. An independent HTTPS publisher added Pan 13.25; Fetch retained the selection and cached two revisions. Saved-head preview showed incoming-only Pan, with trial preparation disabled. Switching to empty `main` cleared review; switching back recovered the scoped base/cache and required a new preview. The native check used saved observations, not a live Console capture. Its fixture history is intentionally retained in private local metadata.

After the native process exited successfully, relaunch restored the OS-backed account without typing. The existing project list automatically chose the matching saved fixture, whose stored current branch was `import-main`; this does not establish a persisted project-selection preference. Shared-base IDs/time and the two-revision cache/head/fetch time were unchanged. No review restored automatically; explicit Preview recomputed incoming-only Pan 13.25 and displayed singular one-field copy. **Copy state capture** stayed disabled with the message “Service history reviews are read only and cannot start the rename drill.” Sign-out cleared review and required service sign-in. The vault remained mode `0600` with zero saved entries; schema-5 local metadata retained one fixture revision, empty `main`, selected `import-main`, and one scoped receipt.

The QA app and disposable service both exited successfully before the whitelisted temporary fixture root and private locator were removed. The browser tab closed and viewport reset. The ordinary app relaunched without the fixture CA and was observed signed out with no selected export. Native fixture observation history remains intentionally in private metadata. Production hosting, complete native semantics, current-live-branch provenance, cross-device identity, and executable pull/apply remain outside these claims.
