# Collaboration and media identity foundations

The service foundations run locally. The [standalone host](SERVICE_HOST.md), [encrypted collaboration runtime](DURABLE_COLLABORATION_SERVICE.md), and [desktop service connection](DESKTOP_SERVICE_SYNC.md) now build on the authorized HTTP boundary and asynchronous metadata client. Hosted deployment and managed delivery remain open. See [revision network sync](REVISION_NETWORK_SYNC.md) for transport scope and validation status.

## Read-only sharing

`createProjectShareLinks` issues a random 256-bit bearer token for one immutable revision, with a caller-chosen expiration bounded by policy. Only a project owner can create, list, revoke, or copy a link. The stored record and listings contain a token digest, not the token. `read` returns only that revision and its manifest; it rechecks expiration, revocation, and project deletion. URLs require HTTPS and put the token in a fragment so a future web client can redeem it without sending it in the initial page request. `copy` writes through a trusted clipboard callback and revokes the link if copying fails. A hosted redemption endpoint, deployed web viewer, and desktop copy control remain open.

## Notifications and activity

`createProjectActivity` records append-only, hash-linked project events and recipient-scoped notification receipts. The combined runtime now commits revision/branch and membership events atomically with domain changes, suppresses no-op/idempotent replay duplicates, and persists explicit read receipts. Authorized project members can page activity and their own inbox over HTTPS; the desktop adds explicit refresh, mark-read, and an opt-in 30-second app-open watch. `pull.completed` has no validated producer. No email, operating-system notification, digest, or delivery while the app is closed is configured.

The combined runtime validates the activity hash chain, recipient receipts, and cross-state references on recovery. Schema-1 collaboration state upgrades to schema 2 with empty activity; it does not backfill or replay history. Standalone callers of `createProjectActivity` still own persistence of its snapshot. Public events contain safe IDs, type codes, and timestamps, omitting recipients, file paths, invitation tokens, and media names. Removed members immediately lose project feed/inbox access. See [project activity](PROJECT_ACTIVITY.md) for cursor scope, capacities, desktop limits, and the passed HTTPS restart proof; all 690 tests, packaging validation, and [browser/native checks](phase-0/project-activity-desktop-observation.json) passed within the documented loopback and app-open limits.

## Membership and deletion

Project ownership moves only to an existing project member who also belongs to its team. The previous owner becomes an editor. `setProjectRole` cannot silently create or remove owners. Owners can remove nonowner members; removal immediately revokes access. Project deletion is a tombstone: it disables authorization, invitation acceptance, and share-link redemption, while retaining immutable history for a future retention and recovery policy. It does not erase stored revisions or media. Account-deletion planning ignores tombstoned projects; team ownership still needs transfer.

## Branch approvals on a self-hosted service

The encrypted collaboration runtime persists branch policies, requests, approvals, scoped creation receipts, and matching activity in combined schema 4. Existing branches start unprotected. A current owner can require zero through five independent approvals with a policy-version compare-and-swap. Saving an unchanged requirement preserves the version and existing requests. A changed policy invalidates requests under its previous version.

History's **Branch approvals** panel selects a service project and branch independently of the local FCPXML or Resolve selection. Refresh reads the current head, policy, staged direct-child revisions, and review requests atomically. An owner/editor can request review of a saved proposal for that exact head and policy. Requests expire after seven days. Current owners/editors can approve except the requester and the proposed revision's author; the service rechecks every approver's current access when publishing. Viewers can read but cannot request, approve, change policy, or publish.

An approval records review; the requester still publishes through the existing queued **Push** or **Retry** action. A protected push uploads immutable metadata, then blocks before moving the branch if approvals are missing. Refresh Branch approvals, choose the saved proposal, request review, and retry the blocked push once enough independent reviewers have approved. Each branch advance is reviewed separately. A head or policy change requires a new request. Publication rechecks current publisher access, candidate parent, head, policy, expiry, and active approvals in the same encrypted transaction as the branch compare-and-swap, applied receipt, and activity. An exact retry of a previously committed compare-and-swap returns its historical acknowledgment without reevaluating expired or revoked approvals or duplicating events; current publisher authorization is still required.

Desktop mutations carry an opaque guard for the selected account, role, branch, last checked head, and policy. Account/access changes clear review evidence, late replies are discarded, and successful mutations require a fresh read before another action. Signed continuation cursors bind the actor, project, branch, head, policy, and page kind. The desktop displays at most 500 requests or candidates per selection. Creation retry keys remain in memory; cross-restart offline review drafts are not provided.

Protection state is bounded to 16 MiB, 10,000 policy versions, 10,000 requests, 20,000 creation receipts, and 100 recorded approvals per request. Capacity failures preserve the prior transaction. The runtime validates policy history, revision/parent bindings, approval identity exclusions, applied branch ancestry, receipts, and matching activity during recovery. These controls publish revision metadata; they do not apply changes inside an editor. Managed hosting and public cross-device deployment remain separate work.

The [disposable live observation](phase-0/branch-approvals-live-observation.json) verifies the actual native queued publish and separate browser reviewer over loopback HTTPS, viewer restrictions, two responsive checks at 1440/768/390 pixels, and signed-out cleanup. The automated HTTPS process proof uses 58 requests across three fresh hosts and three clients and checks exact lost-acknowledgment replay after policy and reviewer-access changes. All 963 full-suite and 576 security tests passed without skips, and package inputs passed validation. Focused renderer/controller integration tests also preserve successful acknowledgments when state events arrive before the action response or the following read fails. These checks use synthetic accounts and immutable observation metadata; they do not establish public deployment or editor apply.

## Media asset identity

`identifyMediaFile` reuses the safe streaming SHA-256 fingerprint, checks file stability, and returns a path-free identity with byte count and explicit asset class and media type. Matching content IDs mean matching observed bytes, while `assetClass` preserves original/proxy distinctions. Storage namespace, cross-project deduplication, resumable transfer, and expected-identity provenance remain open.
