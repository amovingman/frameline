# Collaboration and media identity foundations

The service foundations run locally. The [standalone host](SERVICE_HOST.md), [encrypted collaboration runtime](DURABLE_COLLABORATION_SERVICE.md), and [desktop service connection](DESKTOP_SERVICE_SYNC.md) now build on the authorized HTTP boundary and asynchronous metadata client. Hosted deployment and managed delivery remain open. See [revision network sync](REVISION_NETWORK_SYNC.md) for transport scope and validation status.

## Read-only sharing

The self-hosted service provides owner-created links to one immutable revision. History's **Read-only sharing** panel selects a service project and branch independently of local editor selection. Refresh verifies the current branch head, and **Create and copy link** creates a new link for that exact revision and copies it through the main process. Expiration choices are one hour, one day, seven days, or thirty days; the API accepts durations from one hour through thirty days. Link permissions are always read only.

Anyone holding the link can read the pinned revision's metadata, including captured timeline and clip names and represented properties. The link grants no account, membership, comment, media-byte, history-list, or branch-write access. Moving the branch never retargets an existing link. The desktop lists each link's pinned revision, creation and expiry times, and active/expired/revoked/unavailable status. A current owner can revoke a link. Redemption rechecks expiration, revocation, project tombstones, and the issuer's active account and current owner role; ownership transfer therefore invalidates links issued by the former owner.

The bundled recipient page is served at `/share` over HTTPS. Its 256-bit capability is in the URL fragment, which is not sent with the initial page request. A bundled script immediately removes the fragment from the address and holds it only in the tab. The recipient explicitly chooses **Open shared revision** before a same-origin `POST /shares/redeem` sends the capability in a bounded JSON body. Successful redemption clears the in-memory token. Reloading requires opening the original link again. The page renders plain text, a summary, and expandable full metadata; it cannot apply changes or fetch media. Expiration or revocation prevents a later redemption but cannot erase metadata a recipient already read or copied. The page states that access was checked when it opened.

Static assets and responses use no-store caching, no-referrer policy, no framing, same-origin resources, and a strict content security policy. Fonts are bundled; there are no third-party requests. Anonymous redemption accepts at most 512 body bytes and eight concurrent operations. Per-process limits allow twenty requests per hashed peer per minute and 120 globally per minute, with at most 256 peer buckets. These are bounded single-host controls, not a distributed abuse service.

Encrypted combined schema 6 stores scoped creation receipts, token hashes, immutable revision/manifest bindings, revocations, and matching `share.created`/`share.revoked` activity. Capabilities are derived with a domain-separated HMAC from private persisted service material, so an exact creation retry can recover the same capability after a lost acknowledgment without saving plaintext tokens or duplicating the link. Current owner authorization is still required for that retry. Owner listings, renderer state, application events, and logs contain no bearer URL or token. State is bounded to 8 MiB and 10,000 links with one creation receipt per link. Recovery validates hashes, receipts, references, and matching activity.

A lost creation acknowledgment may leave an active link even if the desktop did not finish copying it; refresh the list before deciding what to do next. Failed-copy retry keys remain private and in memory. A clipboard failure triggers a revoke attempt. The desktop reports either confirmed revocation or the exact link that needs manual revocation if cleanup failed. It never claims a failed write created nothing. Account/access changes clear private review rows, scope guards reject stale commands, and signed pages bind actor/project/branch/head. The desktop displays at most 500 links before requiring a fresh list. Cross-restart offline copy drafts are not provided.

The legacy `createProjectShareLinks` module remains an in-memory reference. This integrated workflow uses `service-share-links.js`, `desktop-share-links.js`, and the existing self-hosted launcher; no public hostname, certificate, hosting provider, or outbound delivery is configured automatically.

The [disposable live observation](phase-0/share-links-live-observation.json) records native one-day link creation/copy, browser one-hour creation/copy, recipient explicit opening, immutable content after a branch advance, native revocation followed by fresh-recipient denial, viewer restrictions, and signed-out cleanup. The recipient view passed 1440/768/390-pixel checks; native owner controls were inspected on the desktop. The separate HTTPS proof issued 62 requests across three hosts and three clients, including expiry under an advanced server clock, former-owner/project-deletion denial, protected-API isolation, and exact capability recovery after a lost creation acknowledgment. The 1,057-test full suite, 670 security tests, and package validation passed without skips. After the singular/plural copy fix, 75 focused viewer/controller/renderer tests passed. These are disposable loopback checks, not a public deployment or physical cross-device trial.

## Notifications and activity

`createProjectActivity` records append-only, hash-linked project events and recipient-scoped notification receipts. The combined runtime now commits revision/branch and membership events atomically with domain changes, suppresses no-op/idempotent replay duplicates, and persists explicit read receipts. Authorized project members can page activity and their own inbox over HTTPS; the desktop adds explicit refresh, mark-read, and an opt-in 30-second app-open watch. `pull.completed` has no validated producer. No email, operating-system notification, digest, or delivery while the app is closed is configured.

The combined runtime validates the activity hash chain, recipient receipts, and cross-state references on recovery. Schema-1 collaboration state upgrades to schema 2 with empty activity; it does not backfill or replay history. Standalone callers of `createProjectActivity` still own persistence of its snapshot. Public events contain safe IDs, type codes, and timestamps, omitting recipients, file paths, invitation tokens, and media names. Removed members immediately lose project feed/inbox access. See [project activity](PROJECT_ACTIVITY.md) for cursor scope, capacities, desktop limits, and the passed HTTPS restart proof; all 690 tests, packaging validation, and [browser/native checks](phase-0/project-activity-desktop-observation.json) passed within the documented loopback and app-open limits.

## Membership and deletion

Project ownership moves only to an existing project member who also belongs to its team. The previous owner becomes an editor. `setProjectRole` cannot silently create or remove owners. Owners can remove nonowner members; removal immediately revokes access. Project deletion is a tombstone: it disables authorization, invitation acceptance, and share-link redemption, while retaining immutable history for a future retention and recovery policy. It does not erase stored revisions or media. Account-deletion planning ignores tombstoned projects; team ownership still needs transfer.

## Branch approvals on a self-hosted service

The encrypted collaboration runtime persists branch policies, requests, approvals, scoped creation receipts, and matching activity in combined schema 6. Existing branches start unprotected. A current owner can require zero through five independent approvals with a policy-version compare-and-swap. Saving an unchanged requirement preserves the version and existing requests. A changed policy invalidates requests under its previous version.

History's **Branch approvals** panel selects a service project and branch independently of the local FCPXML or Resolve selection. Refresh reads the current head, policy, staged direct-child revisions, and review requests atomically. An owner/editor can request review of a saved proposal for that exact head and policy. Requests expire after seven days. Current owners/editors can approve except the requester and the proposed revision's author; the service rechecks every approver's current access when publishing. Viewers can read but cannot request, approve, change policy, or publish.

An approval records review; the requester still publishes through the existing queued **Push** or **Retry** action. A protected push uploads immutable metadata, then blocks before moving the branch if approvals are missing. Refresh Branch approvals, choose the saved proposal, request review, and retry the blocked push once enough independent reviewers have approved. Each branch advance is reviewed separately. A head or policy change requires a new request. Publication rechecks current publisher access, candidate parent, head, policy, expiry, and active approvals in the same encrypted transaction as the branch compare-and-swap, applied receipt, and activity. An exact retry of a previously committed compare-and-swap returns its historical acknowledgment without reevaluating expired or revoked approvals or duplicating events; current publisher authorization is still required.

Desktop mutations carry an opaque guard for the selected account, role, branch, last checked head, and policy. Account/access changes clear review evidence, late replies are discarded, and successful mutations require a fresh read before another action. Signed continuation cursors bind the actor, project, branch, head, policy, and page kind. The desktop displays at most 500 requests or candidates per selection. Creation retry keys remain in memory; cross-restart offline review drafts are not provided.

Protection state is bounded to 16 MiB, 10,000 policy versions, 10,000 requests, 20,000 creation receipts, and 100 recorded approvals per request. Capacity failures preserve the prior transaction. The runtime validates policy history, revision/parent bindings, approval identity exclusions, applied branch ancestry, receipts, and matching activity during recovery. These controls publish revision metadata; they do not apply changes inside an editor. Managed hosting and public cross-device deployment remain separate work.

The [disposable live observation](phase-0/branch-approvals-live-observation.json) verifies the actual native queued publish and separate browser reviewer over loopback HTTPS, viewer restrictions, two responsive checks at 1440/768/390 pixels, and signed-out cleanup. The automated HTTPS process proof uses 58 requests across three fresh hosts and three clients and checks exact lost-acknowledgment replay after policy and reviewer-access changes. All 963 full-suite and 576 security tests passed without skips, and package inputs passed validation. Focused renderer/controller integration tests also preserve successful acknowledgments when state events arrive before the action response or the following read fails. These checks use synthetic accounts and immutable observation metadata; they do not establish public deployment or editor apply.

## Media asset identity

`identifyMediaFile` reuses the safe streaming SHA-256 fingerprint, checks file stability, and returns a path-free identity with byte count and explicit asset class and media type. Matching content IDs mean matching observed bytes, while `assetClass` preserves original/proxy distinctions. Storage namespace, cross-project deduplication, resumable transfer, and expected-identity provenance remain open.


## Team templates

History → **Team templates** works independently of a local export, editor selection, or service branch binding. Refresh available teams, choose one, and load its saved templates. Current team members can read the catalog. A team owner can create or edit a template and create a new project from it; ownership of an individual project does not grant team ownership.

A template contains a name, up to twenty additional empty branches, and allowed media classes. `main` is always included. New templates start with no additional branches or classes. Saving uses an expected version and a scoped retry key; unchanged values preserve the version. Editing a template affects future projects only.

Choose a saved template, enter a new project name, and preview the result. The preview shows the exact branch names and initial media classes. **Create project** requires that reviewed template version and project name. It creates an empty service metadata project owned by the requesting team owner. It does not create an editor project, link a local branch, publish a revision, or upload any media. Linking and media transfers remain separate explicit workflows. A template with enabled media classes cannot create a project unless the service has its optional media backend configured.

Combined encrypted schema 7 commits the new history project, access registration, empty branches, immutable initial media policy, and creation receipt together. The media service reads that committed initial policy whenever no later explicit policy record exists. Template-created projects begin at media-policy version 1; a later project-owner policy save starts at version 2 and takes precedence. Existing projects retain their previous policy behavior. There is no second asset-store write during project creation, and a retry never resets a project's later policy or branch heads.

Creation receipts pin the actor, team, template version, name, original branch list, and original media classes. An exact committed retry returns the same historical receipt even after template edits or project deletion. It cannot create the project again. Current team-owner authorization is required even for a retry. A preview hash is bound to its requesting account and exact template content; it grants no access by itself.

The desktop records a private pending request before sending a save or creation. After a lost acknowledgment or app restart, **Retry pending request** uses the same request key and original reviewed values. It does not automatically replay during startup. A verified service receipt is displayed before local cleanup or follow-up reads, so a failed refresh does not turn a successful creation into a failure. Other writes wait until the pending request is resolved. **Dismiss local retry** requires confirming that the service was checked; it does not undo a saved change, and a new request may create a duplicate. The journal partitions requests by service/account and is excluded from renderer credentials and public logs.

State is bounded to 1,000 saved templates, 10,000 save receipts, 10,000 creation records, and 16 MiB, within the collaboration store's separate total limit. Limits refuse new work; there is no automatic pruning. Valid combined schemas 1–6 migrate with empty template state and preserve their prior domains. No templates or enabled media policies are inferred from historical projects. Backups must retain the entire combined state and the separate asset index together; restoring older state can restore old policy or retry information.
