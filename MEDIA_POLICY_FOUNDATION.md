# Media availability and storage policy foundation

The [personal revision media workflow](PERSONAL_MEDIA.md) now adds canonical dependency capture, checked-location six-state reports, selected-revision transfers, and reference-aware owner collection through the self-hosted CLI. This page records the earlier classifier and desktop per-content policy foundation.

`src/media-storage-policy.js` adds the next five Phase 4 policy behaviors to the local reference service. The outputs contain IDs, states, classes, hashes, and byte counts; they do not expose local paths.

- Availability uses explicit evidence to distinguish `cloud-present`, `collaborator-only`, `local-only`, `missing`, `excluded`, and `archived`. A cloud-present asset can also have a verified local copy; both facts remain visible.
- Per-project sync policy starts with no asset classes enabled. The reference model has a serializable snapshot. The optional self-hosted service now persists owner-managed original, proxy, audio, graphics, and other settings in its encrypted index and exposes them in the desktop; see the integration boundary below.
- A revision download plan includes only required assets. Execution resolves the authoritative selected revision again, rejects added or changed assets, rechecks any claimed local asset, reads only planned cloud chunks, verifies each chunk and the final SHA-256, and writes content-hash-named files without overwriting existing files. The caller must choose a destination and supply the authoritative revision reader. A hosted revision/media manifest binding remains open.
- Relink candidate checks require both the expected asset class and exact size and SHA-256. A proxy cannot satisfy a camera original even if it has the same name or bytes. This produces a decision report; editor project reference rewriting remains unavailable.
- Upload estimates report bytes to upload, bytes reused within the configured storage namespace, bytes excluded by class policy, and current project logical and exclusive storage. The service reports stored usage from verified asset records. Estimates are not billing quotes and do not include transfer overhead or retention charges.

## Self-hosted and desktop integration

The desktop's [Project media panel](DESKTOP_MEDIA_TRANSFERS.md) now displays the linked service project's saved class policy, usage, and manual content-ID availability checks. Owners explicitly save enabled classes; editors and viewers can read the policy. A version compare-and-swap refuses stale policy writes. Disabled classes cannot upload or download, including through previously issued chunk tickets; changing policy retains existing bytes. New projects enable no classes. Migration from the earlier encrypted asset index retains existing assets and partial uploads but starts with no classes enabled, so an owner must enable them before further transfers.

The service reports published logical bytes partitioned into available, archived, and excluded bytes, plus partial-upload count, acknowledged bytes, and declared bytes. Exclusion takes precedence over archive in the partition. These index-derived figures are not disk allocation, billing, quotas, or a new integrity check. Desktop upload review continues to show the selected file's bytes and exact-content reuse estimate before confirmation.

Availability checks describe only the requested content ID in the linked service project: on this service, excluded by project policy, archived, or not on this service. An asset can be both excluded and archived. Owners can archive or restore published media using a compare-and-swap; archive retains bytes and blocks transfers, while restore still respects class policy. This does not implement deletion or retention cleanup.

Local-only, collaborator-only, and globally missing states are not inferred from service lookup. Canonical revision/media bindings, selected-revision downloads, editor relinking, reference-aware deletion, and production storage operations remain open. The integrated workflow passed all 659 tests and packaging validation. A [77-request HTTPS restart proof](phase-0/asset-storage-policy-network-observation.json) verified durable settings, usage, retained bytes, and ticket enforcement; [browser/native checks](phase-0/asset-storage-policy-desktop-observation.json) verified roles, controls, and stale policy edits. Earlier validation results in the linked documents describe their historical milestones.
